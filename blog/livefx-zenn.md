## 1. はじめに

結論から言うと、今回も大成功しました。

改めて、LiveFx は、ライブパフォーマンスにおける演者と観客間のインタラクションを促進するために開発されたデジタル演出ツールです。
本システムの主要な特徴は、演者側の MIDI コントローラーによる画面演出の操作を、リアルタイムに観客のスマートフォンへ視覚効果として同期表示させる点にあります。

滋慶学園グループの入学式プレゼンでの利用を目的として開発されました。
また、保護者を含めた 18 の専門学校グループ、最大 5,000 台の観客用スマートフォンへの同時配信を想定したスケーラブルな設計が求められました。

本稿では、この学生主体となった貴重な開発経験を振り返り、その経緯や所感を共有することを目的とします。
また、記録してきた写真やソースコードの一部を、公開可能な範囲で提示します。
近いうちに、ソースコードを OSS として公開できるようにしたいと思っています。

### サーバーごとの機能

3 アプリの大まかな立ち位置は、`control-pc` が「演出の司令塔」、`back-smartphone` が「スマホ向け配信ハブ」、`front-smartphone` が「観客の描画端末」です。
どれも Node.js / React / TypeScript を使っていますが、責務とプロトコルが明確に分かれています。

#### `front-smartphone`

観客スマホの React アプリ (`front-smartphone`) は、1 つの URL 上で 6 つの画面を切り替えるシングルページ構成です。
オペレーターが `control-pc` から `changePage` イベントを投げると、`back-smartphone` の Socket.IO 経由で `changePage` が届き、`setCurrentPage(page)` で差し替わります。

#### `control-pc`

サーバー側は受け取ったイベントで `currentPage` / `currentPattern` / `currentFilter` / `currentGroups` を記憶し、同じ内容を TCP で `back-smartphone` へフォワードする

| 状態                   | 更新契機                                                        | 用途                                                      |
| ---------------------- | --------------------------------------------------------------- | --------------------------------------------------------- |
| `currentPage`          | `changePage` イベント受信時                                     | 次の接続/再接続クライアントに送る画面情報                 |
| `currentPattern`       | `pattern` / `sendAdjustmentData` / `sendFlexPatternData` 受信時 | 再接続時に演出を復元するためのペイロード (文字列 or JSON) |
| `currentRunUNIXTimeMs` | パターン系イベント受信時                                        | 演出実行の時間基準 (再接続時の相対時刻計算に使う)         |
| `currentFilter`        | `changeFilter` 受信時                                           | フィルターの不透明度 (0-100)                              |
| `currentGroups`        | 演出イベントの `groups` を直接反映                              | 対象グループの一覧 (1-based)                              |

### 荒れ果てた環境の整備期（2025/12/23〜）

最優先でやるべきは環境構築整備でした。
特に以下の項目です。

#### 1. フォーマッターの導入とCIによる強制

もともとフォーマッターを導入していなかったため、ソースコードはかなり自由に書かれていました。
その結果、空行や構文の書き方に不統一が目立ち、コードリーディングに時間がかかる状態になっていました。

私は以前から自分のプロジェクトで husky や lint-staged を使い、コミット前にフォーマットを強制していたため、この対応は比較的スムーズに進めることができました。
また、GitHub Actions を利用して、フォーマットが適用されているかのチェックも行うようにしました。

devcontainer の導入も検討しましたが、今回は採用していません。

理由はいくつかありますが、最も大きいのはエディタ依存の問題です。
devcontainer 自体は仕様としてはエディタ非依存ですが、実際の運用では VSCode の拡張機能に強く依存する形になります。

そのため、Cursor など他のエディタを利用しているメンバーとの間で開発体験に差が生まれる可能性がありました。

また、今回のケースではフォーマッターと CI によるチェックを導入することで、環境差異の問題の大部分は解消できていました。
そのため、Docker ベースの開発環境を新たに整備するコストに対して、得られるメリットは限定的と判断しました。

[https://zenn.dev/risu729/articles/latest-husky-lint-staged](https://zenn.dev/risu729/articles/latest-husky-lint-staged)

#### 2. 通知機能

通知のトリガーとして想定していたのは、「演出が始まるタイミング」です。
このタイミングで通知を行えば、観客にスマホを掲げるよう案内する必要がなくなると考えました。

しかし、最終的にはこの機能は実装しませんでした。
理由はシンプルで、技術的な難易度が高かったためです。

当初はPWAの導入や、いっそのことネイティブアプリ化する案も検討しましたが、
今回のスコープでは必須ではないこと、そして開発コストが非常に大きいことから見送りとしました。

#### 3. コントロールPCの認証機能

実は昨年まで、コントロール PC には認証機能が存在していませんでした。
URL を知っていれば、誰でもアクセスできる状態だったのです。

つまり、理論上は誰でも会場の演出画面を操作できる状態でした。
冷静に考えると、かなり危険な状態です。

ではなぜ実装していなかったのかというと、
「当日にその URL を知る人はいないだろう」という、楽観的な想定に頼っていたためです。

実際の運用では、QR コード入りの封筒を開封するという導線があり、
そこからコントロール PC が指示を送るまでの時間は約 10 秒程度でした。
この短時間で URL を特定するのは現実的ではない、という判断でした。

結果的に問題は発生しませんでしたが、運が良かっただけとも言えます。

今年は時間的な余裕もあるため、この認証機能を正式に実装しました。

```mermaid
sequenceDiagram
    autonumber
    participant Browser as Operator Browser
    participant CPC as control-pc (Express)
    participant SM as Secrets Manager
    Browser->>CPC: GET /api/csrf-token
    CPC-->>Browser: {csrfToken} + Set-Cookie connect.sid
    Browser->>CPC: POST /api/login + csrf header + {password}
    CPC->>SM: ADMIN_PASSWORD は起動時に注入済み
    CPC->>CPC: timingSafeEqual で比較
    alt 成功
        CPC->>CPC: req.session.authenticated = true
        CPC-->>Browser: 200 {message: "Login successful"}
    else 失敗
        CPC-->>Browser: 401 {error: "Invalid password"}
    end
    Browser->>CPC: WSS /ws/control-pc (connect.sid cookie)
    CPC->>CPC: sessionMiddleware で session 復元 → authenticated 確認
    alt 認証済み
        CPC-->>Browser: connection established
    else 未認証
        CPC-->>Browser: Unauthorized (connection error)
    end
```

#### 4. `front-control-pc` と `back-control-pc` を `control-pc` へ統合

この話が出た背景として、もともと本プロジェクトではサーバー数が 4 つあり、構成としてやや複雑でした。

特に control-pc に関してはフロントエンドとバックエンドを分離していましたが、
WebSocket の接続は 1 系統のみであり、分離する必要性は低い状態でした。

一方で、UI と API の両方は必要なため、フロントエンドとバックエンドを一体で扱えるフルスタック構成が求められました。

### 議事録を正確に書き残せない問題（2026/03/05〜2026/03/22）

Notionで取っていた議事録を、開発メンバーで見返す機会がありました。
そこで気づいたのが、「内容に誤りが含まれていた」ということです。

もともと議事録の作成は任意としており、担当者は毎回 1〜2 人程度でした。
その状況で「毎回書くのが間に合わない」という意見が出るのは当然であり、これに対処するためにいくつかの改善案を検討しました。

まず前提として、話す人と書く人は分ける必要があります。
さらに、書く人には一定の理解力も求められます。
しかし、限られたリソースの中でそれを満たすのは容易ではありませんでした。

ここで改めて整理したゴールは、「議事録を正確な履歴として残すこと」です。
このゴールを達成するために、以下のような観点で検討を進めました。

```md
1. **会議設計の改善をどう実践するか**
   - スクライバーの決め方（立候補？ PM 指名？）
   - 休憩のタイミング
   - スクライビングのツール（FigJam とか）
2. **メンバーから意見を集める方法**
   - 全員から集めるか、一部でいいか
   - ツールを Discord スレッドにするか FigJam にするか
   - 意見を PM が精査して議題に上げる仕組みにするか
3. **時間配分と開発の時間確保**
   - 今回の会議で開発の話の時間が足りるか
   - PM に事前に時間配分を決めてもらうか
```

特に重要だと感じたのは、議事録の精度を担保する役割です。
必要であれば会議を一時停止してでも、「正しく記録されているか」を確認するプロセスが不可欠でした。

また、会議運営そのものも見直しました。
事前にレジュメを用意し、議題ごとに時間とゴールを設定する。
議論が発散しそうな場合は別議題として切り出し、その場で扱うか後回しにするかを判断するようにしました。
一方で、グラフィックレコーディングという手法も検討しましたが、リアルタイムでの正確性確認が難しいという理由から見送りました。

続く会議では FigJam を用いたスクライビングも試しました。
会議の流れを視覚的に追いやすいというメリットはあったものの、情報が分散してしまう点が課題となり、最終的には Notion に戻す判断となりました。

```md
スクライビングはfigjamでやる必要はないと仮定してnotionで戻す。
大事なのはファシリテーター。まとめるなら結局ここが大事。
```

### ついに迎えた本番（2026/04/09）

ついに本番当日です。
…が、開始直前にこんなメッセージが飛び込んできました。

```md
waveが会場で順番通りにならないかも
```

原因は、`waveFlex / rippleFlex` の実行順が `schoolId` ベースで決まっていたことにありました。
`Control PC` で指定した `groups` の並び順が、`smartphone` 側に反映されていなかったのです。
対応として、`groups` の配列順をそのまま各端末に渡し、その順序で実行されるように修正しました。

さらに、モニタリング画面上で学校の並び順を変更できるようにし、学校番号と並び順を対応させた JSON をインポート / エクスポートできる仕組みも追加しました。

結果として——

本番 30 分前に再デプロイすることになりました。
（今年もやってしまった…）
とはいえ、無事に動いたので今では笑い話です。

そして、さいたま IT・WEB 専門学校のプレゼンが始まります。
本当にうまくいくのか。
直前のリハーサルでは初歩的なミスもあり、不安はかなり大きい状態でした。

まず、会場の席に配置された封筒の QR コードをスマホで読み取ってもらいます。
多少の戸惑いはありつつも、その後カウントダウンが開始。
会場はざわつき始め、「何が始まるんだろう」という期待感が伝わってきました。

やがて会場が暗転し、単色演出がスタート。

第一印象は、とにかく綺麗でした。

しかし今回は、NTP による時刻同期を導入したことで、完全に統一。
この改善だけでも、体感で 10 倍以上のクオリティ差がありました。
会場からも、驚きの声が上がっていました。

## 7. 失敗・学び

今回は良くも悪くもトラブルが少ないプロジェクトでした。
開発メンバー全体として慎重に進める姿勢があり、安全性は高かったと思います。

一方で、その影響もありPRのマージが滞りがちになり、後続タスクに影響が出る場面もありました。
スピードと安全性のバランスは、最後まで課題として残りました。

### 初動のタスクが重く、新メンバーに入りづらい雰囲気を作ってしまった

今回のプロジェクトは、「前年の構成を整備し直す」ことからスタートしました。
しかしこの作業は、過去のコードにある程度精通していなければ難しい内容でした。

さらに、

- サーバー統合に伴うインフラ再編
- フォーマッターなど、属人化しやすい開発基盤の整備

といった、難易度の高いタスクが初期に集中していました。

その結果、新メンバーはこれらのタスクに関与しづらく、プロジェクトに入り込むきっかけを失ってしまっていました。
加えて、これらのタスクは変更量が多くコンフリクトも発生しやすいため、新規機能の開発は一時的に待たざるを得ない状況になっていました。

#### 改善案

最初から難易度の高い基盤整備に着手するのではなく、あえて新メンバーでも触れる軽量なタスクを用意します。

具体的には、

- UIの微修正
- ログ出力の追加
- 簡単なバグ修正
- ドキュメント整備

など、「プロジェクトに触れる入口」を先に作ります。
その上で、

- 基盤整備は小さく分割する
- ペアやモブで進める

ことで、知識のキャッチアップと並行して進められる状態を作ります。

### 「自分からタスクを取りに行って」 「やりたいのがあったら発言して」は難しいことが多い

本プロジェクトでは、「タスクは自分から取りに行く」方針を取っていました。

しかし実際には、これを実践するのは簡単ではありません。
特に、「指示があれば動ける」タイプのメンバーにとってはハードルが高く、結果としてタスクが自然に消化されることはあまりありませんでした。

一方で、こちらから積極的にタスクを割り振ることもせず、結果的に一部のメンバーだけで開発を進めてしまう場面もありました。
これは、チーム全体として良い状態ではありませんでした。
後半からは、新メンバーを中心に検証などの軽めのタスクを割り振るようにし、徐々に全員が関与できる状態へと改善していきました。

その結果、

- タスクの分散
- PR レビューの活性化
- 開発以外の作業スピード向上

といった効果が見られ、チームの雰囲気も改善されたと感じています。

### デザインチームへの負担が大きかった

デザインチームの人数が限られている一方で、新機能は多く、
デザインタスクが集中してしまっていました。

デザイン領域は知識の属人化が起きやすく、他メンバーが簡単にサポートできる状態ではなかったこともあり、結果として負担が偏る形になってしまいました。

### デザインに時間をかけすぎた

特にインタラクティブ演出とエンドロール動画の制作で顕著でした。

- インタラクティブ演出の確定：3/17
- デザイン完成：3/31
- 本番：その約1週間後

つまり、実装期間は実質 1 週間しかありませんでした。
当然ながら検証の時間も十分に取れず、開発チームとしては大きな不安を抱えたまま進めることになりました。

デザインは非常に重要ですが、それ単体では価値を発揮できません。
実装されて初めて意味を持ちます。
実際には、開発段階で技術的な制約や認識のズレが発生し、想定通りに進まないことの方が多いと感じています。

#### 改善案

デザイン完成を待ってから実装するのではなく、早い段階で“粗い状態”でもいいので共有し、並行して進めます。

- ワイヤーフレーム段階で実装を開始
- 技術的に難しい部分は早めに検証
- 定期的にデザインと実装のすり合わせを行う

また、「デザインの完成」をゴールにせず、「実装できる状態になっているか」を基準に進めます。

### 会議時間が長すぎる問題

この問題は結局最後まで解決しませんでした。
しかし、のちの振り返り会でいいフィードバックがありましたので共有します。

#### 何が起きていたか

- 会議が毎回 3 時間かかる
- 発言者が固定化（ミュートで聞いてるだけで参加しているだけの人が増える）
- レジメの読み上げで終了
- 話が脱線して雑談化

#### 本質

「会議が“何をする場”になのか、明確になっていない」

今回でいえば、「必要な人が、必要な意思決定をする場」であるべきということ。
私は正直、人が多いと安心するので、安心感のために集まる場として機能させてしまっていたとも思います。
ただ、気づきました。

1. 会議の人数 ≠ 会議の価値
人が多いほど安心できる会議は、たいてい誰も責任を持っていない
2. 「全員参加」は設計放棄
全員呼ぶのは親切ではなく、設計をサボっているだけだった
3. 会議の参加者は“結果”として決まる
ここめっちゃ大事👇
何を決めるか決める
誰が決めるか決める
だから参加者が決まる
👉 順番が逆だと崩壊する

■ 原則

会議＝「必要な人が、決めるために集まる場」

共有（進捗・数値）は事前に読むもの

■ 改善

時間を区切る

例：課題Aは30分で強制終了


読み上げ禁止

例：資料は事前にNotionで共有


ゴールを絞る

例：「今日はUI方針だけ決める」


人数を絞る

例：意思決定者＋担当者だけ参加


ファシリを置く

例：「それ今やらないです」と止める人

### ツールはなるべくシンプルに統一すべき

今回特に課題となったのは、Notion と GitHub Issue の使い分けです。

- コーディングタスク → GitHub Issue
- それ以外 → Notion

という運用をしていましたが、「コーディングタスク」の定義は人によって異なり、次第に境界が曖昧になっていきました。

その結果、Notion側にも開発タスクが増え、タスクが分散する状態になりました。
タスクが複数の場所に存在すると、

- 現在の全体像が把握しづらい
- 優先度管理が難しい

といった問題が発生します。
PMとして全体を把握する立場だったため、この点にはかなり苦労しました。

また、Notionはタスクの履歴を時系列で追いづらく、完了通知の挙動にも違和感がありました。

現在も両者は併用されていますが、将来的にはGitHubへ統一したいと考えています。
Projectsやマイルストーンなどの機能により、プロジェクト管理との親和性が高いためです。

### `gh pr merge --squash --admin` 事件

![livefx-admin-merge](/images/livefx-2026-zenn/livefx-2026-merge.png)

これは完全に自分のやらかしです。

通常、このコマンドを実行することはほとんどありません。
しかし今回は、AIによって実行されてしまいました。
もちろん最終的な責任は自分にあります。

リポジトリにはmainブランチの保護ルールがあり、本来は 2 人以上の承認がなければマージできません。
しかし、admin 権限を持っている場合、この制約をバイパスできます。

今回の PR は、main にマージしないと検証できない内容だったため、その意図が AI に伝わり、`--admin` 付きでマージされてしまったと考えられます。
幸い大きな問題は発生せず、すぐに rebase で対応しました。

この件を受けて、

- AIのAuto-Run Modeを無効化
- Cursor Hooksでコマンド実行を制限

といった対策を行いました。
詳細は以下の記事にまとめています。

[https://zenn.dev/tkszenn/articles/cafc72cd8d1754#cursor-hooks](https://zenn.dev/tkszenn/articles/cafc72cd8d1754#cursor-hooks)
